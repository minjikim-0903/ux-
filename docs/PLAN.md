# 기획안: AI가 만든 UX 검증 + 실제 행동 데이터 수집

상태: MVP 개발 중 · 
서비스 이름 :미정

## 1. 한 줄 요약

**"내 AI가 만들어준 UX, 괜찮을까?"**
서비스 링크를 넣으면 유저가 어디서 망설이는지 진단해 주고, 
그 진단을 실제로 고쳐본 결과까지 모아서 **이론이 아니라 실제 행동에서 나온 UX 근거 데이터**를 쌓는 서비스

## 2. 왜 만드나요

### 문제
- AI로 화면은 금방 만들어요. 그런데 그 화면의 UX가 괜찮은지는 만든 사람도 모름.
- 서비스를 만든 사람이 자기 서비스의 기획 의도나 UX 원칙을 잘 모르는 경우가 많음.
- 개발자도 뚝딲 코드로 만드는데 UXUI 기본기가 없는 경우가 많으거라고 예상함.
- 프로덕트 디자이너들도 요즘은 AI를 많이 사용하고 있는데 행동분석에 추측할 가능성이 있음.

### 기존 방법의 한계
| 방법 | 한계 |
|---|---|
| UX 이론 (닐슨 노먼 그룹 같은 가이드, 책) | 주로 이론적인 개념. |
| 행동 분석 도구 (Amplitude, Clarity, 핫자 등) | 실제 행동은 플레이로 확인가능함. 그런데 직접 유저 한명 한명 찾아보고, 해석해야 한다. 정량적 데이터로도 분석할 수 있지만, 이 역시 결국 추측의 단계로 실행해봐야만 알 수 있다. |

### 우리가 하려는 것
**추측하지 않기.** 진단을 보고 → 일단 실행해 보고 → 결과로 판단해요.
그 결과를 쌓으면 "책에서 읽은 원칙"이 아니라 **"실제로 해봤더니 이렇게 됐다"는 직접 근거**가 돼요.

## 3. 누구를 위한 서비스인가요

- AI(바이브코딩)로 서비스를 직접 만든 1인 메이커, 초기 창업자
- UX 전문가가 없는 작은 팀
- 공통점: 화면은 있는데 "이게 맞나?"를 판단할 근거가 없다.
- 이탈하는건 알겠는데 어디를 개선해야할지 뾰족하게 알기 어렵다.

## 4. 어떻게 동작하나요

```
① 링크 + 서비스 설명 입력
      ↓
② 실제 브라우저로 화면을 열어 스크린샷 + 화면 요소 수집
      ↓
③ AI 진단: 문제 진단 → 이럴 가능성이 있어요(가설) → 이렇게 해보세요(제안) → 기대 효과
      ↓
④ 사용자가 제안을 실행 (고쳐보기)
      ↓
⑤ 결과 확인: 실제 행동이 바뀌었나?
      ↓
⑥ 데이터 누적 → 다음 진단의 근거가 됨
```

- **서비스 설명(프롬프트)**: 기획을 아는 서비스 담당자 (개발, 디자이너, pm,po 등) "어떤 서비스인지, 어디가 문제인지 추측한 내용 등 "를 자유롭게 적으면 그 맥락에 맞춰 제안한다.
- **AI 제작 여부 체크**: "AI로 만든 서비스인가요?" + 사용 도구(Lovable, Bolt, v0, Cursor, Claude Code, 기타)를 고르게 한다. 바이브코딩 화면만 따로 분석할 수 있고, "도구별로 자주 나오는 문제" 같은 데이터도 된다. (자세한 기준은 9-4)
- **화면 위 표시**: 스크린샷 위에 문제 위치를 ①②③ 핀으로 보여줌.

## 5. 무엇을 모으나요

데이터가 쌓이는 단위는 **"화면 하나에 대한 진단 → 실행 → 결과"** 한 세트예요.

| 구분 | 데이터 | 성격 |
|---|---|---|
| 화면 | 링크, 페이지 유형(랜딩·요금제·가입·결제 등), 스크린샷, 화면 요소(버튼·가격·입력칸 위치와 문구) | 사실 |
| 맥락 | 사용자가 적은 서비스 설명, 목표 | 사실 |
| 진단 | 문제, 가설, 제안, 기대 효과, 행동심리 원리 | **AI 추정** |
| 실행 | 제안을 적용했는지, 무엇을 어떻게 바꿨는지 | 사실 |
| 결과 | 바꾸기 전과 후의 실제 행동 (클릭률, 다음 단계 이동률, 이탈, 망설임 신호) | **실제 행동** |

> ⚠️ **중요:** 진단만 쌓으면 "AI 의견 모음"이에요. **실행과 결과가 연결된 데이터만** 우리가 말하는 "직접 근거"가 돼요. 그래서 실행과 결과를 기록하게 만드는 것이 이 서비스의 핵심 과제예요.
실행은 했는데 결과를 어떻게 수집할것인가는 고민해봐야할 과제임.
아마 ai가 만들어준 ux가 어떤식으로 만들어지는지는 파악할 수 있을거라고 생각함.

> **결정 (결과 수집 방법):** 사이트 주인이 자기 사이트에 **스니펫(코드 한 줄)을 직접 설치**하는 방식만 쓴다. 숫자 직접 입력이나 파일 업로드는 하지 않는다. 설치하지 않으면 측정하지 않는다. 측정 원칙은 8번 참고.


## 6. 쌓인 데이터를 어떻게 쓰나요

1. **근거 있는 제안**: "비슷한 다른 서비스의 요금제 화면에서 추천 표시를 붙인 뒤 다음 단계 이동률이 올랐어요(사례 N건)"처럼, 이론 대신 실제 사례를 근거로 제안해요.
2. **진단 정확도 개선**: AI가 예측한 기대 효과와 실제 결과를 비교해서, 맞은 진단 규칙은 강화하고 틀린 규칙은 고쳐요.
3. **패턴 발견**: 책에 없는, 실제 행동에서만 보이는 망설임 패턴을 찾아요.

## 7. 근거는 3단계로 보여준다

리포트의 제안마다 근거가 어디서 왔는지 구분해서 표시한다. 처음에는 이론과 공개 사례로 시작하고, 우리 데이터가 쌓이면 점점 그쪽 비중을 늘린다.

| 표시 | 내용 | 수집 방법 |
|---|---|---|
| **[이론]** | 행동심리 원리, UX 가이드(닐슨 노먼 그룹 등) | 진단 규칙(`rubric.ts`)에 정리 |
| **[공개 사례]** | 인터넷에 공개된 실제 개선 사례 (무엇을 바꿨고 결과가 어땠는지) | 직접 수집해서 DB에 저장. **요약 + 출처 링크만** 저장하고 원문·이미지는 복사하지 않는다 (저작권) |
| **[우리 데이터 N건]** | 이 서비스 사용자들이 실제로 고쳐보고 측정한 결과 | 스니펫 측정 + 공유 동의한 것만 |

- 공개 사례는 성공한 것만 공개되는 경향이 있다. 그래서 숫자는 참고용으로 보여준다.
- 우리 데이터는 다른 사람에게 보여줄 때 **통계로만** 보여준다. 예: "요금제 화면 사례 23건, 평균 +5%p". **"A사 사이트에서는…"처럼 특정 사이트를 드러내지 않는다.**

## 8. 데이터와 측정 원칙

**우리가 가져가는 게 아니라, 사이트 주인이 직접 켜고, 직접 보고, 공유 여부도 직접 정한다.**

### 측정 (스니펫)
- **설치는 주인만 할 수 있다.** 자기 사이트 코드에 직접 붙여야 동작하므로, 설치 자체가 소유 확인이 된다.
- **측정 시작과 중지는 주인이 누른다.** 누른 기간에만 기록한다.
- **결과는 주인만 본다.** 전후 비교는 그 사이트 주인의 리포트에만 나온다.
- **공유는 따로 동의받는다.** "내 결과를 익명으로 근거 데이터에 기여하기"는 별도 체크박스, **기본값은 꺼둔다.**
- **최소 수집:** 클릭, 스크롤, 머무름, 다음 단계 이동 같은 행동만 기록한다. **입력칸에 쓴 내용은 절대 기록하지 않는다.** IP는 저장하지 않고 무작위 익명 ID만 쓴다.
- 보안이 걸린 페이지(로그인 뒤 화면)는 우리가 접근하지 않는다. 측정할지는 주인이 그 페이지에 스니펫을 넣을지로 정한다.
- 방식은 GA, Clarity와 같다. 주인이 설치하고, 주인이 자기 사이트 방문자에게 알린다. 그래서 주인에게 **자기 처리방침에 넣을 문구 템플릿**을 제공한다.

### 진단 결과와 스크린샷
- **본인만 본다.** Supabase **익명 로그인**으로 로그인 화면 없이 사용자마다 ID를 주고, DB와 저장소에 "내 ID로 만든 진단만 볼 수 있다"는 규칙(RLS)을 건다. 나중에 이메일 로그인을 붙이면 익명 계정을 그대로 정식 계정으로 바꾼다.
- 남의 공개 페이지 스크린샷은 진단을 요청한 사람에게만 보여준다.
- 정해진 기간이 지나면 지운다 (기간은 정해야 함, 예: 1년).

### 진단 대상 제한
- **공개 페이지만** 진단한다. 로그인이 필요한 화면은 읽지 않는다.
- **robots.txt나 이용약관으로 자동 수집을 금지한 사이트는 제외**한다.
- **불법·유해 사이트(도박, 성인, 피싱, 불법 상품 등)는 진단하지 않는다.** 여러 방법을 겹쳐 쓴다.
  1. AI 판별: 진단할 때 사이트 종류를 먼저 판단하고 해당하면 거절한다.
  2. 악성 사이트 검사: Google Safe Browsing 같은 API로 피싱·악성코드를 거른다.
  3. 차단 목록: 걸린 도메인은 저장해서, 다음부터는 AI를 부르기 전에 막는다.
- 내부망 주소(localhost, 사설 IP)는 막는다. ✅ 구현됨

## 9. 법적 체크리스트

> 법률 자문이 아니라 준비할 항목 정리. **사용자 행동 데이터를 실제로 모으기 시작하는 시점(로드맵 3단계) 전에 전문가 검토를 받는다.** (개인정보보호위원회 상담, 스타트업 무료 법률 상담 프로그램 등)

### 9-1. 개인정보 처리방침 (우리 서비스)
개인정보를 거의 모으지 않는 구조라 짧게 만들 수 있다. 개인정보 포털(privacy.go.kr)의 작성 지침과 만들기 도구로 초안을 만든다.

| 항목 | 이 서비스라면 |
|---|---|
| 처리 목적 | UX 진단, 서비스 개선, 익명 통계 |
| 수집 항목 | 입력한 링크, 서비스 설명, 익명 사용자 ID, (스니펫) 익명 행동 기록 |
| 보유 기간과 파기 | 예: 1년 뒤 삭제 |
| 처리 위탁과 **국외 이전** | Vercel, Supabase(아일랜드 리전), Anthropic. 모두 해외 업체라 **국외 이전을 꼭 적는다** |
| 이용자의 권리 | 열람·삭제 요청 방법 |
| 쿠키·자동 수집 | 스니펫이 무엇을 기록하는지 |
| 책임자 연락처 | 이메일 |

### 9-2. 이용약관 기본 항목
| 항목 | 내용 |
|---|---|
| 서비스 내용 | 공개 페이지를 AI로 분석해 UX 개선안을 제안 |
| 이용자 의무 | 공개 페이지만 넣기, 불법·공격 목적 금지 |
| 분석 결과의 성격 | AI 추정이며 결과를 보장하지 않음 (면책) |
| **데이터 활용 동의** | 진단 결과를 **익명화해서 통계와 근거 데이터로 쓴다**. 이 서비스의 목적이 데이터 수집이므로 가장 명확하게 적는다 |
| 지식재산권 | 스크린샷 속 화면의 권리는 원래 사이트에 있고, 분석 목적으로만 씀 |
| 삭제 요청 | 사이트 주인이 요청하면 해당 페이지 데이터를 지움 |
| 이용 제한 | 불법·유해 사이트는 진단하지 않으며 이용을 제한할 수 있음 |
| 기타 | 서비스 변경·중단, 책임 제한, 문의처 |

### 9-3. 해외 방문자 (GDPR)
GDPR은 유럽연합(EU)의 개인정보 보호법이다. 회사가 한국에 있어도 유럽 사람을 대상으로 하면 적용된다. 핵심은 **꼭 필요하지 않은 추적은 방문자가 동의하기 전에 시작하면 안 된다**는 것이다. 처음에는 한국 사용자 대상이라 한국 개인정보보호법이 기준이다. 유럽 방문자가 있는 사이트가 스니펫을 쓰면 그 사이트에 동의 배너가 필요하다고 안내한다.

### 9-4. AI 제작 여부 구분
자동으로 100% 구분하는 건 불가능하다. (예: Cursor나 Claude Code로 만들어 자기 도메인에 배포한 사이트)
- **주된 방법: 본인 확인.** 입력할 때 AI 제작 여부와 사용 도구를 체크한다.
- **보조 수단: 자동 추정.** 캡처할 때 흔적을 찾아 "AI 제작 추정" 표시만 붙인다.
  - 도메인: `*.lovable.app`, `*.vercel.app`, `*.netlify.app`, `*.replit.app` 등
  - 화면 흔적: "Edit with Lovable" 같은 배지, 도구가 넣는 메타 태그
  - 코드 흔적: shadcn/ui + Tailwind 기본 스타일 (사람이 만든 사이트도 많이 써서 근거로는 약함)

## 10. 로드맵

| 단계 | 내용 | 상태 |
|---|---|---|
| 0. 진단 MVP | 링크 입력, 브라우저 스크린샷, AI 진단 리포트(문제→가설→제안→효과), 화면 핀 | ✅ 로컬 동작 (실제 AI 진단은 API 크레딧 충전 후 검증 필요) |
| 1. 진단 저장 | Supabase 익명 로그인, 진단 저장(화면·맥락·진단), 본인만 보기(RLS), AI 제작 여부·도구 체크, 불법·유해 사이트 차단 | ✅ 구현 (익명 로그인 켜기 필요. robots.txt 확인은 아직) |
| 1-1. 근거 DB | 공개 사례와 이론을 수집해서 리포트 근거로 연결 (7번) | 1단계와 함께 |
| 2. 실행 기록 | 리포트에서 "이거 적용했어요" 체크 + 무엇을 바꿨는지 기록 | 예정 |
| 3. 결과 수집 | 주인이 설치하는 스니펫. 측정 시작·중지, 전후 비교, 공유 별도 동의 (8번). **시작 전 법률 검토** | 예정 |
| 4. 근거 기반 제안 | 쌓인 "진단→실행→결과" 데이터로 비슷한 화면에 사례 기반 제안 | 예정 |

**당장의 목표:** 0~2단계까지 돌려서 "진단을 보고 실제로 실행해 보는" 흐름이 되는지 확인하기.

## 11. 성공 지표

| 지표 | 의미 |
|---|---|
| 진단 수 | 사람들이 링크를 넣고 진단 버튼까지 누르는가 |
| 제안 실행률 | 진단을 보고 실제로 고쳐보는가 (가장 중요) |
| 결과 기록률 | 고친 뒤 스니펫으로 결과까지 남기는가 |
| 효과 확인 비율 | 실행한 제안 중 실제 행동이 좋아진 비율 |

## 12. 남은 질문과 리스크

- **결과를 정말 제안 덕분이라고 말할 수 있을까?** 트래픽이 적은 서비스는 전·후 비교만으로 판단하기 어렵다. 어느 정도면 "근거"라고 부를지 기준이 필요하다.
- **스니펫 설치 동기:** 설치는 귀찮은 일이다. 설치하면 무엇을 더 얻는지(전후 비교 리포트 등)가 분명해야 한다.
- **초기 데이터 부족:** 데이터가 쌓이기 전에는 AI 추정 + 이론 + 공개 사례로 가치를 줘야 한다.
- **비용:** 진단 한 번 = 이미지(단계 수만큼, 장마다 크기에 비례) + 페이지 글자 + AI 답변. 크레딧 충전 후 첫 진단의 실제 사용량(`usage`)으로 한 번당 비용을 계산한다. 브라우저는 지금은 자체 서버라 별도 요금이 없고, 외부 브라우저 서비스를 쓰면 시간 단위 비용이 생긴다.
- **보관 기간:** 진단과 스크린샷을 얼마나 보관할지 정해야 한다.
- **서비스 이름:** 미정.

## 13. 검토 중인 아이디어

- **AI에게 시킬 프롬프트 복사:** 제안마다 "Cursor·Lovable에 붙여 넣을 프롬프트"를 만들어 준다. 타깃은 AI에게 시켜서 고치므로, 실행이 가장 쉬워지고 실행률이 오른다.
- **포지셔닝 (UX vs AX):** 본질은 사람의 경험(UX)이고 AI 전환(AX)은 배경. 메시지에서는 "내 유저가 왜 가입을 안 하지?"를 앞세운다.
- **데이터를 AI 생성 규칙으로 되돌리기:** 쌓인 결과를 "AI가 처음부터 더 좋은 UX를 만들게 하는 규칙"으로 제공한다.
- **에이전트 경험:** 나중에는 "AI 에이전트가 이 화면을 잘 쓸 수 있나?"까지 검사한다.
