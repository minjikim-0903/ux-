# 기획안: AI가 만든 UX 검증 + 실제 행동 데이터 수집

> 작성일 2026-11-18 · 상태: MVP 개발 중 · 서비스 이름 미정

## 1. 한 줄 요약

**"내 AI가 만들어준 UX, 괜찮을까?"**
링크를 넣으면 유저가 어디서 망설이는지 진단해 주고, 그 진단을 실제로 고쳐본 결과까지 모아서 **이론이 아니라 실제 행동에서 나온 UX 근거 데이터**를 쌓는 서비스예요.

## 2. 왜 만드나요

### 문제
- AI로 화면은 금방 만들어요. 그런데 그 화면의 UX가 괜찮은지는 만든 사람도 몰라요.
- 서비스를 만든 사람이 자기 서비스의 기획 의도나 UX 원칙을 잘 모르는 경우가 많아요.

### 기존 방법의 한계
| 방법 | 한계 |
|---|---|
| UX 이론 (닐슨 노먼 그룹 같은 가이드, 책) | 일반 원칙이에요. "내 화면에서 실제로 그런지"는 알려주지 않아요. |
| 행동 분석 도구 (Amplitude, Clarity 등) | 실제 행동은 보여줘요. 그런데 직접 연결하고, 찾아보고, 해석해야 해요. 해석 단계에서 결국 다시 추측하게 돼요. |

### 우리가 하려는 것
**추측하지 않기.** 진단을 보고 → 일단 실행해 보고 → 결과로 판단해요.
그 결과를 쌓으면 "책에서 읽은 원칙"이 아니라 **"실제로 해봤더니 이렇게 됐다"는 직접 근거**가 돼요.

## 3. 누구를 위한 서비스인가요

- AI(바이브코딩)로 서비스를 직접 만든 1인 메이커, 초기 창업자
- UX 전문가가 없는 작은 팀
- 공통점: 화면은 있는데 "이게 맞나?"를 판단할 근거가 없어요.

## 4. 어떻게 동작하나요

```
① 링크 + 서비스 설명 입력
      ↓
② 실제 브라우저로 화면을 열어 스크린샷 + 화면 요소 수집
      ↓
③ AI 진단: 문제 진단 → 이럴 가능성이 있어요(가설) → 이렇게 해보세요(제안) → 기대 효과
      ↓
④ 사용자가 제안을 실행 (고쳐보기)
      ↓
⑤ 결과 확인: 실제 행동이 바뀌었나?
      ↓
⑥ 데이터 누적 → 다음 진단의 근거가 됨
```

- **서비스 설명(프롬프트)**: 사용자가 기획을 잘 몰라도 "어떤 서비스인지, 뭘 늘리고 싶은지"를 자유롭게 적으면 그 맥락에 맞춰 제안해요.
- **화면 위 표시**: 스크린샷 위에 문제 위치를 ①②③ 핀으로 보여줘요.

## 5. 무엇을 모으나요

데이터가 쌓이는 단위는 **"화면 하나에 대한 진단 → 실행 → 결과"** 한 세트예요.

| 구분 | 데이터 | 성격 |
|---|---|---|
| 화면 | 링크, 페이지 유형(랜딩·요금제·가입·결제 등), 스크린샷, 화면 요소(버튼·가격·입력칸 위치와 문구) | 사실 |
| 맥락 | 사용자가 적은 서비스 설명, 목표 | 사실 |
| 진단 | 문제, 가설, 제안, 기대 효과, 행동심리 원리 | **AI 추정** |
| 실행 | 제안을 적용했는지, 무엇을 어떻게 바꿨는지 | 사실 |
| 결과 | 바꾸기 전과 후의 실제 행동 (클릭률, 다음 단계 이동률, 이탈, 망설임 신호) | **실제 행동** |

> ⚠️ **중요:** 진단만 쌓으면 "AI 의견 모음"이에요. **실행과 결과가 연결된 데이터만** 우리가 말하는 "직접 근거"가 돼요. 그래서 실행과 결과를 기록하게 만드는 것이 이 서비스의 핵심 과제예요.

## 6. 쌓인 데이터를 어떻게 쓰나요

1. **근거 있는 제안**: "비슷한 요금제 화면에서 추천 표시를 붙인 뒤 다음 단계 이동률이 올랐어요(사례 N건)"처럼, 이론 대신 실제 사례를 근거로 제안해요.
2. **진단 정확도 개선**: AI가 예측한 기대 효과와 실제 결과를 비교해서, 맞은 진단 규칙은 강화하고 틀린 규칙은 고쳐요.
3. **패턴 발견**: 책에 없는, 실제 행동에서만 보이는 망설임 패턴을 찾아요.

## 7. 로드맵

| 단계 | 내용 | 상태 |
|---|---|---|
| 0. 진단 MVP | 링크 입력, 브라우저 스크린샷, AI 진단 리포트(문제→가설→제안→효과), 화면 핀 | ✅ 로컬 동작 (실제 AI 진단은 API 크레딧 충전 후 검증 필요) |
| 1. 진단 저장 | 모든 진단을 Supabase에 저장 (화면, 맥락, 진단) | 다음 작업 |
| 2. 실행 기록 | 리포트에서 "이거 적용했어요" 체크 + 무엇을 바꿨는지 기록 | 예정 |
| 3. 결과 수집 | 사용자 사이트에 넣는 가벼운 행동 수집 스크립트(스니펫). 리포트의 기대 효과 지표를 바꾸기 전·후로 자동 측정 | 예정 |
| 4. 근거 기반 제안 | 쌓인 "진단→실행→결과" 데이터로 비슷한 화면에 사례 기반 제안 | 예정 |

**당장의 목표:** 0~2단계까지 돌려서 "진단을 보고 실제로 실행해 보는" 흐름이 되는지 확인하기.

## 8. 성공 지표

| 지표 | 의미 |
|---|---|
| 진단 수 | 사람들이 링크를 넣는가 |
| 제안 실행률 | 진단을 보고 실제로 고쳐보는가 (가장 중요) |
| 결과 기록률 | 고친 뒤 결과까지 남기는가 |
| 효과 확인 비율 | 실행한 제안 중 실제 행동이 좋아진 비율 |

## 9. 열린 질문과 리스크

- **실행·결과를 어떻게 기록하게 만들까?** 사용자가 직접 기록하는 건 귀찮아요. 스니펫 자동 측정이 필요할 수 있어요.
- **결과를 정말 제안 덕분이라고 말할 수 있을까?** 트래픽이 적은 서비스는 전·후 비교만으로 판단하기 어려워요. 어느 정도면 "근거"라고 부를지 기준이 필요해요.
- **개인정보와 동의**: 행동 수집 스크립트를 넣으면 그 사이트 방문자의 데이터를 다루게 돼요. 개인정보 처리 방침과 동의 절차가 필요해요.
- **남의 링크 분석**: 본인 서비스가 아닌 링크도 넣을 수 있어요. 공개 페이지만 읽고, 로그인 화면은 읽지 않아요. 이용 약관에 범위를 적어야 해요.
- **초기 데이터 부족**: 데이터가 쌓이기 전에는 AI 추정만으로 가치를 줘야 해요.
- **비용**: 진단 한 번마다 AI 비용(이미지 포함)과 브라우저 실행 비용이 들어요.
- **서비스 이름**: 미정.

## 10. 기술 구성 (현재)

- **앱**: Next.js 15 (Vercel 배포)
- **DB**: Supabase (연결 완료, 테이블 아직 없음)
- **화면 수집**: Playwright (로컬에서만 동작, Vercel용 설정 필요)
- **AI 진단**: Claude API
